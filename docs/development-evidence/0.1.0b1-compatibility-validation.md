# `0.1.0b1` compatibility validation evidence

This is operator-controlled development evidence. It is not MNCS/MNCDS conformance, independent
evaluation, protected custody, witnessing, certification, governance approval, promotion, or
sandbox assurance.

## Baseline

The frozen baseline is `origin/main` commit `fe92aa1`. A detached worktree with its own editable
virtual environment proved that imports resolved to that worktree. The first attempted baseline
environment reused an editable environment from another checkout and was discarded rather than
treated as evidence.

```bash
PATH="$PWD/.venv/bin:$PATH" ./scripts/check.sh
PATH="$PWD/.venv/bin:$PATH" python scripts/benchmark-micro-verifiers.py --iterations 25
git diff --check
```

Ruff formatting/lint, strict mypy, 267 tests, sdist, wheel, and `git diff --check` passed. Pytest
reported one upstream Pydantic Settings unresolved-forward-reference warning during MCP schema
construction.

## Compatibility audit and changes

Current `main` already had frozen version-1 record models/schema, canonical serialization and
identity projections, the immutable later-`0.1` corpus, raw-ledger-first migration, future-version
and type/context rejection, transactional storage/recovery, CLI/MCP shared dispatch, an operation
inventory digest, MCP mode separation, and facade characterization.

The audit found three bounded gaps:

1. early unversioned `0.1` workflow-like records created before `subject_type` could reproduce
   their historical identity but failed current required-field validation;
2. malformed TOML and a missing configuration path escaped stable Forge error codes; and
3. public configuration, complete CLI arguments/defaults/decoders, all MCP schemas/resources,
   Provider Protocol request/response envelopes, all public facade signatures, and packaging
   metadata were characterized separately but lacked one explicit release-boundary check.

The migration now adds only the historically valid candidate subject after authenticating the old
projection. It cannot infer project scope from an identity string. The aggregate snapshot strips
schema titles/descriptions and excludes help/error prose, prompts/tool descriptions, timestamps,
paths, environment values, callables, internal layout, performance, and package release version.

## Migration and adversarial results

- all 14 frozen later-`0.1` records still verify and load without rewrite;
- early workflow result, final evaluation, and bundle variants preserve identity and status;
- normalized early records round-trip deterministically;
- a missing subject paired with project-looking identity text remains candidate-scoped;
- an explicit project subject cannot use the early candidate identity projection;
- unknown legacy fields remain non-normative extensions;
- current unknown fields, missing authority fields, future versions, and type/context mismatches
  fail closed with their existing specific errors; and
- a raw-valid legacy ledger containing `CERTIFIED` verifies as a raw chain, then fails semantic
  migration with `RECORD_STATUS`.

The fixture `SHA256SUMS` digest remained
`e29304525455e71307db8722e5d4273807619b32f94a7e53b031626c9b754fff`.

## Installed-wheel mixed-history check

The built `mncs_forge_mcp-0.1.0a2-py3-none-any.whl` was installed without dependencies into an
isolated virtual environment that inherited the already installed dependency set. The check ran
from `/tmp`, asserted `mncs_forge.__file__` was under that environment's `site-packages`, copied the
frozen fixture, and verified:

- 14 historical entries and their known identities loaded;
- one current schema-1 candidate committed through `LocalRecordStore`;
- the resulting mixed ledger contained 15 valid entries;
- the complete historical ledger byte sequence remained an exact prefix;
- every historical immutable file remained byte-identical;
- early-result migration worked in memory; and
- schema version `"999"` failed with `UNSUPPORTED_RECORD_VERSION`.

The package version remained `0.1.0a2` under the repository's existing release policy. The
repeatable artifact verifier for this evidence now lives in `scripts/verify-package.py`; the
broader package-stability follow-up is tracked as Task 9B and does not change the closed public
compatibility boundary.

## Joern comparison

Joern `4.0.583` parsed the baseline source before edits and the final source with `PYTHONSRC`.
The same committed queries were run against both CPGs:

```bash
joern-parse --language PYTHONSRC src --output /tmp/mncs-forge-b1-<baseline-or-post>.cpg
joern --script scripts/joern/b1-compatibility-boundary.sc \
  --param cpgFile=/tmp/mncs-forge-b1-<baseline-or-post>.cpg
joern --script scripts/joern/task2-record-flow.sc --param cpgFile=<same-cpg>
joern --script scripts/joern/task4-storage-flow.sc --param cpgFile=<same-cpg>
joern --script scripts/joern/task6-operation-dispatch.sc --param cpgFile=<same-cpg>
```

The focused comparison found:

- `_legacy` remained called only by `MigrationRegistry.normalize`; its condition count changed
  from five to seven for authenticated subject compatibility;
- `parse_record` remained reached by record-file and ledger-entry normalization;
- all 13 current `new_record` call locations were unchanged and remained in the intended
  application/recovery/verifier constructors;
- all 11 application/verifier persistence sites remained `RecordStore.commit` calls;
- `load_config` gained one catch branch, from one to two, for stable malformed-TOML handling;
- CLI retained one registry `invoke`, MCP retained tool/resource invokes, and all 25 facade calls
  remained centralized in operation handlers; and
- raw ledger reads still reached `_verify_raw_records` before `normalize_ledger_entry`.

Joern emitted known Python CFG order-fallback warnings for `try`/`catch`/`finally`, `break`, and
`continue`, plus Java restricted/`Unsafe` API warnings. Generic-name call linking (especially
`append`) remained noisy, and no data-flow or absence-of-path claim was supported strongly enough
to treat as proof. Executable tests establish value ordering, identity/status preservation,
current-version metadata, interface schemas, and transactional behavior.
